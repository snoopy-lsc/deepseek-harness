# 公开多用户 Harness 设计

[English](2026-10-10-public-team-harness-design.md) | 中文

## 目标与范围

本提案把一台 Linux 服务器用于公开注册的 Harness 服务，提供完整的编程代理工具、平台承担的模型额度、每人私有的 Session 和工作区，以及安装到所有用户实例的统一界面插件。

任何访客完成邮箱验证和反自动化检查后都可以注册。注册不保证立即获得运行容量：达到服务器配置上限时，实例准入可以拒绝或排队。通过 Git 共享项目；Harness Session、凭据和工作区仍由每位用户独占。

现有 Harness Web 进程仍按单操作者应用使用。每位获准使用的用户拥有独立 Harness 进程和私有运行环境。本设计不把用户授权逻辑加入现有 Session API 或代理循环。

## 部署与职责

```text
Browser → Caddy HTTPS + authentik → team router → per-user isolated Harness
per-user isolated Harness → model quota proxy → platform model
```

authentik 负责注册、邮箱验证、验证码、登录、账号状态和不可变用户 ID。Caddy 负责 TLS、每次 HTTP 请求和 WebSocket 握手的前置认证，以及覆盖客户端传入的身份请求头。应用流量只发往团队路由受权限保护的 Unix socket。即使代理配置出错，路由也拒绝缺失、重复、格式错误或未获授权的身份。

团队路由是安装到专用 `dsh` profile 的树外 Cordis bundle。它负责身份与实例的映射、Harness 启动令牌交换、HTTP 和 WebSocket 转发、cookie 路径改写、容量准入，以及给用户显示就绪或拒绝状态。现有 Web server 只注册精确的升级路径，不能按任意用户前缀路由，因此该 bundle 自己持有私有 HTTP server。它不持有平台模型主凭据，也不以 root 身份运行。

独立的最小权限配置服务负责创建宿主机账号、私有存储和隔离运行环境的生命周期。它只接受路由提交的已认证不透明用户 ID，由此生成安全的账号名和服务名，不使用显示名称或邮箱，并让并发请求具备幂等性。路由不能向配置服务提交 shell 命令、文件路径、镜像或任意 systemd 服务名。

每位用户的运行环境具有独立 Linux 服务账号，以及使用 gVisor 运行时的 OCI 容器。容器内有一个 `dsh --profile web` 进程、私有 `DSH_HOME`、一个或多个私有 Git 工作区，以及本地转发组件；后者用于连接容器网络空间内只监听 loopback 的 Web CLI。仅挂载该用户自己的可写存储。容器拿不到宿主机管理 socket、平台模型密钥或其他用户的数据卷。CPU、内存、进程数、磁盘和网络限制都是必填的部署配置；限制缺失或无法执行时拒绝启动。公开准入之前必须在 Linux 上验证 gVisor 中的完整 Web 与工具流程。

模型额度代理位于用户运行环境之外，持有平台模型凭据。运行环境只拿到用于访问该代理的短期、用户专属凭据。代理在每次请求前预留上限，结束后根据模型提供方报告的用量结算；拿不到实际用量时扣除预留额度。必填的正数配置规定单人和全站的每日 token 额度及并发请求上限。额度耗尽或计量存储不可用时拒绝新的模型请求；任何请求都不能绕过计量。

统一界面 bundle 使用已公开的浏览器 `dsh.client` 和 Slot 接口，并安装到每位用户的 Web profile。它负责产品品牌和公共导航；登录页使用 authentik 的品牌配置。按此前约定，隐藏特定 DeepSeek 官方控件属于后续界面改动，不削弱身份与额度规则。

## 请求与生命周期规则

已认证用户请求 `/` 时重定向至 `/u/<不透明ID>/`。路由在每次 HTTP 请求和升级时核对该用户是否拥有路径，转发前去掉 `/u/<不透明ID>/`，保留公开 Host 和 Origin，并且只转发到该用户的 loopback Web 进程。未知路径、缺失身份和跨用户路径都拒绝访问。

一个小型 Web profile Cordis 插件从 `ctx.connection` 获取 Harness 认证 URL，在关闭常规令牌 URL 打印的情况下，通过私有进程管理通道发送启动令牌。路由向匹配实例完成令牌交换；令牌不会出现在浏览器 URL 或日常日志中。得到的 Harness cookie 只适用于 `/u/<不透明ID>/`，在 HTTPS 端添加 `Secure`，并保留 `HttpOnly` 和 `SameSite=Strict`。路由不会在用户之间替换 cookie 或令牌。重启会更换启动令牌；已有签名 cookie 可能在到期前继续有效，但每次新请求仍需要通过外部认证。

完成验证注册后，首次获准访问的请求在该身份专属锁下配置或唤醒一个实例。并发首次访问等待同一次操作。配置失败不能留下可路由的半成品实例；重试会核对已完成的账号、目录和运行环境步骤。空闲实例可以停止，数据继续保留。停用账号会拒绝新请求并停止运行环境；另行确认的账号删除操作会在部署所配置的恢复期后清除工作区和 Session。

Caddy 对每次新请求和 WebSocket 握手进行认证。已有 WebSocket 的最长存活时间是 60 秒，之后必须重新认证连接。停用账号和退出登录会拒绝下一次请求或重连，已打开的连接最长仍可持续 60 秒。浏览器切换身份后不能与旧用户路径建立新连接。

全站活动实例数达到上限时，新用户收到容量提示，系统不创建运行环境。单人资源耗尽时，只停止该用户的运行环境，不影响其他人的数据。路由和额度代理提供健康状态与容量信息，但公开响应和日常日志不泄露身份、凭据、令牌、模型提示词或 Session 内容。

## 打包与升级

团队路由、模型额度代理、运行环境配置集成、Web profile 令牌发布器和界面 bundle 是各自有版本的部署包；路由与两个 Web bundle 使用 Cordis 插件 API，不修改 Harness 代理循环或 Session 存储。每位用户的 profile 安装同一组已测试的 bundle 版本。升级 Harness 时先在非生产 profile 验证兼容性和迁移，再逐步升级用户实例，保留各自的 `DSH_HOME` 和 Git 工作区。bundle 接口变化需要明确升级插件；接口不变时不需要给 Harness 打源码补丁。

实现分为可独立验证的工作：身份与路由、配置与隔离运行环境、模型计量、统一界面与部署集成。四部分都通过下面的 Linux 检查后才开放公开注册。开发顺序不意味着先对外提供功能不完整的服务。

## 验证与发布条件

- 无密钥本机测试启动两个 Web 进程，证明 cookie、HTTP 和 WebSocket 路径隔离；已有的两进程探针提供初步证据，但不是生产身份认证测试。
- 身份测试在 Caddy 到路由的入口拒绝伪造、缺失、重复、过期及跨用户身份输入，覆盖升级请求和账号切换。
- Linux 集成测试使用真实服务完成公开注册、邮箱验证、首次登录配置、并发首次访问、进程重启、空闲唤醒、账号停用和宿主机重启。
- 隔离测试确认一位用户不能通过 Harness 工具、插件安装、Git、文件 API 或直接网络访问读取其他用户的数据或平台模型主凭据；gVisor 或必需限制不可用时运行环境拒绝启动。
- 额度测试覆盖并行预留、流取消、缺失用量报告、个人额度耗尽、全站额度耗尽和计量存储故障，并防止超额调用。
- 浏览器测试通过公开路径加载插件界面并重连 WebSocket；登录页与应用使用同一套产品品牌。
- 公开注册启用前，部署检查核对 TLS、authentik 安全更新、邮箱与验证码配置、受保护的 Unix socket、资源限制、备份恢复和容量。

## 备选方案与限制

单个共享 Harness 进程需要在 Connection、Session、Workspace、凭据和每种执行能力中全面加入身份检查，不属于本设计。单靠 Linux 账号仍让公开代码处于同一宿主机执行环境，因此还需每人独立的隔离容器。静态的每人一条反向代理规则可以省去团队路由代码，但无法以此规模支持开放自助注册和自动准入。

单台服务器容量有限，也是单点故障。本设计在容量满时拒绝新实例并保留已有数据；它不承诺无限注册、高可用、对已打开 WebSocket 消息的瞬时撤权，或抵御所有容器逃逸。公开上线需要专用 Linux 验证主机，以及处理安全更新和滥用的运维机制。
